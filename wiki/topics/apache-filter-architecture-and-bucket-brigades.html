Apache Filter Architecture and Bucket Brigades

概念

**Apache Filter Architecture and Bucket Brigades** は、Apache HTTP Server においてリクエストおよびレスポンスデータを効率的かつモジュール化された方法で処理するための基盤アーキテクチャです。

データは「バケット（Bucket）」と呼ばれるデータ片の連結リストである「バケットブリゲード（apr_bucket_brigade）」として管理され、登録されたフィルタの連鎖（フィルタチェーン）を順次通過しながら加工・送信されます。

なぜ重要か

このアーキテクチャにより、データの生成、変換、送信の各フェーズを独立したモジュールとして分離できます。例えば、レスポンスの特定範囲のみを切り出す処理（ap_byterange_filter）や、HTTP/1.1 のチャンクエンコーディング（ap_http_chunk_filter）などのプロトコル処理を、コアのコンテンツ生成ロジックから完全に独立したフィルタとして実装し、必要に応じて動的にチェーンへ挿入することが可能になります。

関与するモジュール

  • module:include (フィルタ管理の基本構造体の定義)
  • module:modules/http (HTTP プロトコル固有のフィルタ実装)
  • module:server (コアフィルタおよびフィルタ処理基盤)

主要エンティティ

  • **symbol:include/util_filter.h#ap_filter_rec_t**: フィルタの定義情報（名前、実行関数、型、プロトコル制約など）を保持する構造体。フィルタチェーンの構築や登録に使用されます。
  • **symbol:modules/http/byterange_filter.c#ap_byterange_filter**: HTTP Range リクエストを処理し、レスポンスボディを要求されたバイト範囲に切り出して送信する出力フィルタ。
  • **symbol:modules/http/chunk_filter.c#ap_http_chunk_filter**: HTTP/1.1 のチャンク転送エンコーディングを適用し、レスポンスボディをチャンク形式に変換して下流へ渡す出力フィルタ。

エンドツーエンドの流れ

フィルタチェーン全体の構築から破棄に至る完全なエンドツーエンドの制御フローは、提供されたソース情報からは完全には特定されていません。しかし、データ処理における部分的な流れは以下の通りです。

1. **フィルタの登録**: ap_register_input_filter や ap_register_output_filter などの関数により、ap_filter_rec_t に基づくフィルタがシステムに登録されます。 2. **フィルタの呼び出し**: フィルタチェーンの実行時、各フィルタ（ap_byterange_filter や ap_http_chunk_filter など）は、自身のコンテキスト（ap_filter_t）と処理対象のバケットブリゲード（apr_bucket_brigade）を受け取ります。 3. **データの加工と伝播**:

  • フィルタはブリゲード内のバケットを走査し、データの解析や加工（ヘッダーの付与、データの切り出し、チャンク化など）を行います。
  • 加工されたブリゲードは、ap_pass_brigade を介して次のフィルタ（下流）へ渡されます。
  • ストリームの終了（EOS バケットの検出）などの特定の条件に達した場合、フィルタは ap_remove_output_filter を呼び出して自身をチェーンから削除します。

重要な不変条件

  • **フィルタの順序**: フィルタは ap_filter_type に基づいてソートされ、チェーン内での実行順序が決定されます。
  • **サブリクエストの制限**: AP_FTYPE_CONNECTION 以上の型を持つフィルタは、サブリクエスト内では使用できません。
  • **バイトレンジ処理の前提条件**: ap_byterange_filter が動作するためには、ブリゲード内に EOS（End of Stream）バケットが存在し、かつ全バケットの長さが確定している必要があります。長さが不明（-1）なバケットが含まれる場合、処理はスキップされます。
  • **スタック変数の寿命**: ap_http_chunk_filter 内の chunk_hdr はスタック上に確保され、transient バケットとしてブリゲードに挿入されるため、関数スコープを抜ける前に下流でデータが処理（またはコピー）される必要があります。
  • **エラー時のチャンク抑制**: HTTP_BAD_GATEWAY エラーが発生した場合、bad_gateway_seen が設定され、クライアントが不完全なレスポンスを正常終了と誤認するのを防ぐために、最終チャンクマーカー（0\r\n\r\n）の付与が抑制されます。

よくある落とし穴

  • **フィルタ順序の不整合**: フィルタの登録順序や型定義（ap_filter_type）が不適切な場合、意図しない順序でフィルタが実行され、データ破損や予期しない挙動を招く可能性があります。
  • **未確定のバケット長によるスキップ**: パイプなどからデータ長が不明なバケットが渡された場合、ap_byterange_filter は安全のために処理をスキップし、元のデータをそのまま通過させます。これにより、意図したレンジ制限が適用されないことがあります。
  • **スタックメモリの不正参照**: transient バケットにスタック上のデータを割り当てた際、そのバケットが下流のフィルタで適切に処理される前に呼び出し元関数が終了すると、メモリ破壊やセグメンテーションフォールトの原因になります。
  • **エラーハンドリング時の不完全なレスポンス**: バックエンドエラー（HTTP_BAD_GATEWAY など）が発生した際に、適切に最終チャンクマーカーを抑制しないと、クライアント側で不正なデータを正常なレスポンスとして受け取ってしまうリスクがあります。
