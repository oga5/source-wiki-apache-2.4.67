Request Lifecycle and Hook Dispatching

概念

Request Lifecycle and Hook Dispatching は、Apache HTTP Server がクライアントから HTTP リクエストを受信し、それを処理してレスポンスを返し、接続をクリーンアップするまでの一連のプロセスと、その過程で各モジュールの処理（フック）を呼び出す仕組みを指します。このライフサイクル全体を通じて、リクエストの状態やコンテキストは request_rec 構造体によって一元管理されます。

なぜ重要か

Apache HTTP Server は極めてモジュール化されたアーキテクチャを採用しています。リクエストの解析、認証、ハンドラの実行、エラー処理、そして最終的なデータのフラッシュにいたるまで、すべてのフェーズが共通のライフサイクルに沿って実行されます。このライフサイクルとフックのディスパッチ機構を理解することは、モジュール間で情報を安全に共有し、リクエストを正しく処理・終了させるために不可欠です。

関与するモジュール

提供された情報に基づくと、以下のモジュールがこのライフサイクルに関与しています。

  • module:include (コアデータ構造 request_rec の定義を提供)
  • module:modules/http (HTTP リクエスト処理の実装、エラーハンドリング、プロセスの統括)
  • module:server (設定およびフックディスパッチの基盤)

主要エンティティ

  • **symbol:include/httpd.h#request_rec**: 単一の HTTP リクエストのライフサイクル全体を通じて、リクエストの状態、ヘッダー、URI、メソッド、フィルタチェーンなどの情報を保持・共有する中核的なデータ構造。
  • **symbol:modules/http/http_request.c#ap_process_request**: HTTP リクエスト処理の標準的なエントリポイント。リクエストの実行と、接続状態の最終的なフラッシュ処理を統括します。
  • **symbol:modules/http/http_request.c#ap_die**: リクエスト処理中に発生したエラーを処理し、適切なエラーレスポンスを生成するための汎用ハンドラ。

エンドツーエンドの流れ

提供されたエンティティから確認できるリクエスト処理の流れは以下の通りです。

1. **リクエスト処理の開始**: modules/http/http_core.c や modules/http2/h2_c2.c などの呼び出し元から ap_process_request が呼び出されます。 2. **リクエストの実行**: ap_process_request は内部で ap_process_async_request を呼び出し、request_rec に基づいて実際のフック実行やハンドラ処理を行います。 3. **エラーハンドリング（必要時）**: 処理中にエラーが発生した場合、ap_die が呼び出され、エラーのステータスコード（例: HTTP_INTERNAL_SERVER_ERROR）と request_rec を用いて適切なエラーレスポンスが生成されます。 4. **フラッシュとクリーンアップ**: ap_process_request は、接続に未処理の入力データがない場合、出力フィルタチェーンに対してフラッシュバケットを送信し、バッファを強制的にフラッシュします。また、統計情報の更新（ap_time_process_request）や、リクエスト専用メモリプール（apr_pool_t）の解放が行われます。

*注意: フックがディスパッチされる具体的な順序（URI翻訳、アクセス制御、コンテンツハンドラの決定など）の完全な詳細や、ap_process_async_request 内部の具体的なエンドツーエンドのフローは、提供されたモジュールの範囲内では完全には開示されていません。*

重要な不変条件

  • **有効なリクエストレコードの存在**: ap_process_request や ap_die を呼び出す際、引数として渡される request_rec は常に有効な構造体ポインタでなければなりません。
  • **メモリ管理の自動化**: request_rec 内の多くの文字列やデータは、リクエスト専用のメモリプール（apr_pool_t）に割り当てられています。このプールはリクエスト終了時に自動的に解放されるため、モジュール開発者が手動で解放してはなりません。
  • **エラー処理時のステータス整合性**: ap_die を呼び出す前に、request_rec の status フィールド（r->status）が適切に設定されている必要があります。

よくある落とし穴

  • **メモリの二重解放**: request_rec のプールで管理されているメモリを手動で解放しようとすると、メモリ破損の原因となります。
  • **エラー処理の無限再帰**: ap_die はエラー処理中に再帰的に呼び出される可能性があるため、呼び出し元では無限再帰を避ける制御が必要です。また、エラー発生時にフィルタチェーンの状態が変更される可能性があるため、呼び出し後のフローには注意が必要です。
  • **タイムアウトによるフラッシュ失敗**: ap_process_request 内でのフラッシュ処理（ap_pass_brigade）中に APR_TIMEUP が発生することがあります。これはネットワーク切断や DoS 攻撃の可能性を示唆しますが、処理自体は継続されるため、ログの監視が必要です。

次に読む場所

  • include/httpd.h (request_rec の詳細な構造体定義とフィールドの役割)
  • modules/http/http_request.c (ap_process_request や ap_die の具体的な実装)
  • server/config.c (フックの登録とディスパッチ機構の仕組み)
