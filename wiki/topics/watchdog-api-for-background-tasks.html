Watchdog API for Background Tasks

概念

Watchdog API for Background Tasks は、Apache HTTP Server においてバックグラウンドタスクを定期的に実行するための共通フレームワークです。プロセスやスレッドを跨いだタスク管理を抽象化し、登録されたコールバック関数に対して状態遷移（STARTING, RUNNING, STOPPING）を通知しながら定期実行を制御する仕組みを提供します。

なぜ重要か

バックグラウンドで動作する定期タスク（ハートビート監視など）を、各モジュールが個別にスレッド管理や排他制御を実装することなく、安全かつ統一された方法で実行できるようにします。 特に、シングルトンモードによるプロセス間排他制御（ミューテックスを使用）をサポートしており、複数プロセスが存在する環境でも特定のタスクが重複して実行されるのを防ぐことができます。また、APR_DECLARE_OPTIONAL_FN を使用しているため、モジュールのロード状態に依存しない安全な呼び出しが可能です。

関与するモジュール

  • module:modules/core (具体的には mod_watchdog)

主要エンティティ

  • **symbol:modules/core/mod_watchdog.h#ap_watchdog_t**: バックグラウンドタスクを実行するためのウォッチドッグインスタンスを保持する不透明な構造体（Opaque struct）です。
  • **symbol:modules/core/mod_watchdog.c#wd_worker**: 各 Watchdog インスタンス専用のワーカースレッドのメインループとして機能する関数です。

エンドツーエンドの流れ

1. **インスタンスの取得**: 利用するモジュールは、ap_watchdog_get_instance を呼び出して ap_watchdog_t インスタンスを取得します。 2. **コールバックの登録**: ap_watchdog_register_callback を介して、実行間隔（interval）と実行したいコールバック関数（ap_watchdog_callback_fn_t）をインスタンスに紐付けます。 3. **スレッドの起動**: mod_watchdog 内部の wd_startup 等から ap_thread_create を経由して、専用のワーカースレッドである wd_worker が起動されます。 4. **初期化と開始処理**: wd_worker は、シングルトンモードが有効な場合は apr_proc_mutex_trylock を用いてプロセス間排他制御のロック獲得を試みます。ロック獲得後、AP_WATCHDOG_STATE_STARTING 状態で登録済みのコールバック関数を順次実行します。 5. **メインループの実行**: wd_worker は AP_WD_TM_SLICE（100ms）間隔でループを実行します。

  • MPM の停止状態を監視します。
  • 各コールバックの経過時間を計算し、設定された interval を超過していれば AP_WATCHDOG_STATE_RUNNING 状態でコールバックを実行します。
  • コールバックが未登録の場合は、ap_run_watchdog_step フックを実行します。

    • 6. **終了処理**: MPM の停止（AP_MPMQ_STOPPING）などを検知してループを抜けた後、AP_WATCHDOG_STATE_STOPPING 状態でコールバックを実行し、獲得していたロックを解放してスレッドを終了します。

重要な不変条件

  • **メモリプールの有効性**: wd_worker の実行中、スレッド生成時に渡された w->pool は常に有効でなければなりません。
  • **シングルトンモードの排他制御**: シングルトンモードで動作する場合、w->mutex を用いたプロセス間排他制御のロックが獲得できるまで、wd_worker は待機ループを継続します。
  • **MPM 停止時の即時終了**: MPM の状態が AP_MPMQ_STOPPING になった場合、wd_worker は速やかにメインループを終了しなければなりません。
  • **カプセル化の維持**: ap_watchdog_t は不透明な構造体として定義されているため、外部モジュールから直接メンバにアクセスすることは禁止されており、必ず提供されている API を介して操作する必要があります。

よくある落とし穴

  • **デッドロックの危険性**: シングルトンモードで使用する場合、内部でプロセス間ミューテックスが使用されます。コールバック関数内で長時間のロック保持を行うと、デッドロックを引き起こす原因になります。
  • **実行間隔の遅延**: コールバック関数内で重い処理や長時間のブロックが発生すると、同一の Watchdog インスタンスに登録されている他の処理を含め、全体の実行間隔に遅延が生じます。
  • **インスタンス取得の失敗**: ap_watchdog_get_instance が失敗した場合、有効なインスタンスは取得できず、以降の登録処理などは行えません。
