WebDAV Repository and Locking Engine

概念

WebDAV Repository and Locking Engineは、Apache HTTP Server（httpd）の mod_dav モジュール群において、WebDAVリソースのプロパティ管理（ライブプロパティおよびデッドプロパティ）と、リソースに対する排他的・共有的なロック制御を提供するシステムです。 このエンジンは、ファイルシステムベースの永続化機構（DBMなど）を抽象化し、リクエストのコンテキスト（request_rec）やメモリプール（apr_pool_t）と連携しながら、一貫したプロパティ操作（PROPFIND, PROPPATCH）およびロック管理を実現します。

なぜ重要か

WebDAVプロトコルでは、複数のクライアントによる同時編集からリソースを保護するための「ロック管理」と、リソースに関連付けられたメタデータを保持する「プロパティ管理」が不可欠です。 このエンジンは、データベース（DBM）へのアクセスを抽象化し、遅延オープン（Deferred Open）などの最適化を行うことで、不要なI/Oを削減しつつ、トランザクションの整合性（PROPPATCH における検証・実行・コミット/ロールバック）を保証します。これにより、堅牢で効率的なWebDAVサーバー機能の提供が可能になります。

主要エンティティ

本エンジンを構成する主要なデータ構造は以下の通りです。

  • **symbol:modules/dav/main/props.c#dav_propdb**:

    • WebDAVプロパティ操作のコンテキストを保持する構造体。ライブ/デッドプロパティの管理、トランザクション処理、名前空間の解決、およびロックデータベース（dav_lockdb）との連携を統合します。

  • **symbol:modules/dav/fs/lock.c#dav_lockdb_private**:

    • ファイルシステムベースのロックデータベース（DBM）へのアクセス状態（リクエスト、プール、パス、オープン状態、DBハンドルなど）を管理するプライベート構造体。

  • **symbol:modules/dav/fs/lock.c#dav_lock_private**:

    • ロックデータベース内での検索や識別に使用される、ロックに関連付けられたプライベートなキー情報（apr_datum_t key）を保持する構造体。

  • **symbol:modules/dav/fs/lock.c#dav_locktoken**:

    • WebDAVロックを一意に識別するためのUUID（apr_uuid_t）を保持するラッパー構造体。

エンドツーエンドの流れ

提供された情報からは、リクエストの受信から最終的なレスポンス送信に至る完全なエンドツーエンドの制御フローの全容は完全には明らかになっていません。しかし、部分的な流れとして以下が判明しています。

1. **プロパティデータベースの初期化と遅延オープン**: dav_popen_propdb 等により dav_propdb コンテキストが作成されます。この際、deferred フラグが有効な場合、実際のプロパティ操作が必要になるまでデータベースのオープンは遅延されます。 2. **プロパティの解決と操作**: dav_find_liveprop を通じてライブプロパティプロバイダーを特定し、存在しない場合はデッドプロパティとして処理されます。 3. **PROPPATCH トランザクション**: プロパティの更新時、検証（validate） -> 実行（exec） -> コミット/ロールバック（commit/rollback）の順で処理され、失敗時には dav_rollback_item により状態が復旧されます。 4. **ロックデータベースの操作**: dav_lockdb_private を通じて、必要に応じてロックデータベースがオープンされ、dav_locktoken（UUID）や dav_lock_private（DBMキー）を用いてロックレコードのロードや比較、保存が行われます。 5. **クリーンアップ**: 処理の終了時には dav_close_propdb を呼び出し、リソースの解放や内部サブリクエスト（subreq）の破棄を確実に行います。

重要な不変条件

  • **メモリ管理の局所性**: dav_propdb や dav_lockdb_private 内のメモリ割り当ては、関連付けられたプール（r->pool や指定された pool）に紐付いて行われなければなりません。
  • **リソースの確実な解放**: dav_propdb を使用してサブリクエスト（subreq）を生成した場合、必ず dav_close_propdb を呼び出して適切に破棄する必要があります。
  • **ロックトークンの一意性**: dav_locktoken 内の apr_uuid_t は、ロック操作の文脈において一意性を保証する識別子として機能する必要があります。
  • **データベースの整合性**: dav_lockdb_private の db ハンドルが非NULLであることは、データベースが正常に開かれていることを示し、書き込み操作は書き込み可能モードで開かれている場合にのみ許容されます。

よくある落とし穴

  • **サブリクエストのリーク**: dav_propdb の利用後に dav_close_propdb の呼び出しを怠ると、内部で生成されたサブリクエスト（subreq）や関連リソースが解放されず、メモリリークの原因となります。
  • **トランザクション失敗時の不完全な復旧**: PROPPATCH の複雑なエラーハンドリングにおいて、エラーの伝播が不完全な場合、ロールバックが正しく機能しない可能性があります。
  • **名前空間プレフィックスへの依存**: プロパティ値内の名前空間は ns<index> 形式に変換されるため、クライアント側で特定のプレフィックス（接頭辞）の文字列に依存した実装を行うと、互換性の問題が発生します。
  • **破損したDBMキー**: dav_lock_private が保持する key（apr_datum_t）が指すDBM内のデータが破損している場合、後続のロックデータベース操作が予期せず失敗する可能性があります。
