Multi-Processing Modules (MPM) Architecture & Lifecycle

概念

**Multi-Processing Modules (MPM)** は、Apache HTTPD においてネットワークポートのバインド、クライアントからの接続の受け入れ、およびそれらを処理するプロセスやスレッドの管理（並行処理モデル）をカプセル化するためのアーキテクチャです。

提供されたモジュール群（event, prefork, worker）は、それぞれ異なる並行処理アプローチを実装しています。例えば、event MPM は非同期イベント駆動モデルを採用し、prefork はスレッドを使用しないマルチプロセスモデル、worker はマルチプロセスとマルチスレッドのハイブリッドモデルを提供します。

なぜ重要か

Apache HTTPD が稼働する多様なオペレーティングシステムや、異なるシステム要件（高並行性、低メモリ消費、スレッドセーフではないサードパーティ製モジュールとの互換性など）に対して、コアの HTTP 処理ロジックを変更することなく、最適な実行モデルを選択・適用できるようにするために極めて重要です。

関与するモジュール

  • module:server/mpm (MPM 全般の共通基盤)
  • module:server/mpm/event (非同期イベント駆動型 MPM)
  • module:server/mpm/prefork (前もってプロセスをフォークする非スレッド型 MPM)
  • module:server/mpm/worker (マルチプロセス・マルチスレッドのハイブリッド型 MPM)

主要エンティティ

本トピックに関連する主要なソースファイルおよびシンボルは以下の通りです。

  • **server/mpm/event/event.c** / **server/mpm/prefork/prefork.c** / **server/mpm/worker/worker.c**: 各 MPM の具体的なライフサイクルと並行処理ロジックが実装されているソースファイル。
  • **symbol:server/mpm/event/event.c#child_main**: 生成された子プロセスのメイン処理を担当する関数。スコアボードの再オープン、シグナル処理の設定、スレッドの生成・管理などを行います。
  • **symbol:server/mpm/event/event.c#clean_child_exit**: 子プロセスが終了する際に呼び出され、クリーンアップ処理（event_note_child_stopped の呼び出しなど）を実行して安全にプロセスを終了させます。
  • **symbol:server/mpm/event/event.c#perform_idle_server_maintenance**: サーバーの稼働状況（アイドル状態のプロセスやスレッドの数）を監視し、必要に応じて新しい子プロセスを生成（make_child）したり、不要なプロセスに終了シグナルを送信したりして、適切なプロセス数を維持します。
  • **symbol:server/mpm/event/event.c#set_thread_limit**: 設定ファイルからスレッド数の上限（ThreadLimit）を設定するためのディレクティブハンドラ。

エンドツーエンドの流れ

提供されたシンボル情報から、event MPM におけるプロセス管理とライフサイクルの一部分の流れが確認できます。

1. **アイドルサーバーの維持管理**: メインループ（server_main_loop など）から定期的に perform_idle_server_maintenance が呼び出されます。この関数は現在の負荷状況を評価し、必要に応じて make_child を呼び出して新しい子プロセスを起動します。 2. **子プロセスの起動と初期化**: make_child から起動された子プロセスは child_main を実行します。child_main 内部では、ap_reopen_scoreboard による共有メモリ（スコアボード）の再オープン、ap_fatal_signal_child_setup によるシグナルハンドラの設定、および ap_thread_create によるワーカースレッドの生成が行われます。 3. **子プロセスのクリーンな終了**: エラーの発生やシャットダウン指示、またはプロセスの寿命に達した場合、clean_child_exit が呼び出され、リソースの解放と終了ステータスの通知が行われます。

*注意: 親プロセスの初期化から全体のシャットダウン、および prefork や worker における詳細なエンドツーエンドの全ライフサイクルフローは、提供された情報からは完全には明らかになっていません。*

重要な不変条件

  • **コマンドコンテキストの制限**: set_thread_limit などの設定関数は、設定ファイル内の適切なコンテキスト（サーバー設定など）でのみ実行されるよう、ap_check_cmd_context による検証が行われます。

*注意: スレッド制限（ThreadLimit）やサーバー制限（ServerLimit）の相互関係、およびプロセス生成・破棄時における排他制御などの詳細な不変条件は、提供された情報からは完全には明らかになっていません。*

よくある落とし穴

*注意: 提供されたシンボル情報および静的解析データからは、開発時や運用時に陥りやすい具体的な落とし穴（デッドロック、リソースリーク、シグナル競合など）の詳細はまだ十分に解析されておらず、未確定です。*
