Multi-Processing Modules (MPM) and Process Lifecycle

概念

Multi-Processing Modules (MPM) は、Apache HTTPD がネットワークポートをバインドし、クライアントからのリクエストを受け付け、それを処理する子プロセスやスレッドのライフサイクルを管理するためのコアアーキテクチャです。HTTPD は、実行環境や要求されるパフォーマンス特性に応じて、異なる並行処理モデル（マルチプロセス、マルチスレッド、非同期イベント駆動など）を MPM を通じて切り替えることができます。

なぜ重要か

Web サーバーの並行処理能力、メモリ使用量、および安定性は、選択された MPM とそのプロセスライフサイクル管理に直接依存します。例えば、スレッドセーフでないサードパーティ製モジュールを安全に実行するためには prefork が必要であり、大量のキープアライブ接続を効率的に処理するためには event が不可欠です。これらプロセスの適切な生成、維持、およびクリーンなシャットダウンを制御することは、サーバーの信頼性を担保する上で極めて重要です。

関与するモジュール

本トピックには、以下のモジュールが関与しています。

  • module:server/mpm (MPM の共通基盤)
  • module:server/mpm/event (非同期イベント駆動モデルの実装)
  • module:server/mpm/prefork (ノンスレッド、マルチプロセスモデルの実装)
  • module:server/mpm/worker (マルチプロセス・マルチスレッドのハイブリッドモデルの実装)

主要エンティティ

プロセスライフサイクルと MPM の制御に関わる主要なソースコードおよびヘッダーは以下の通りです。

  • **include/ap_mpm.h**: MPM の共通インターフェース、クエリ関数（ap_mpm_query など）、および各種状態定数を定義します。
  • **server/mpm/event/event.c**: リクエスト処理をリスナースレッドとワーカースレッドに分離し、非同期 I/O を用いてプロセスを管理する event MPM のコア実装。
  • **server/mpm/prefork/prefork.c**: 1つの子プロセスが1つの接続を処理する、スレッドを使用しない prefork MPM のコア実装。
  • **server/mpm/worker/worker.c**: 複数の子プロセスがそれぞれ複数のワーカースレッドを持つ、ハイブリッド型の worker MPM のコア実装。

エンドツーエンドの流れ

1. **初期化と起動**: 親プロセスが起動し、設定ファイルを読み込んだ後、ap_mpm.h で定義されたインターフェースを介して、選択された MPM（event, prefork, worker のいずれか）が初期化されます。 2. **プロセスの生成**: 各 MPM は、設定された初期プロセス数に基づき、子プロセスをフォーク（Fork）します。 3. **リクエストの受付と処理**:

  • prefork では、各プロセスが直接接続を受け付けます。
  • worker および event では、プロセス内のスレッド（またはリスナースレッド）が接続を受け付け、ワーカースレッドに処理を割り当てます。

    • 4. **プロセスの維持と回収**: 親プロセスは、稼働中のアイドルプロセス/スレッド数を監視し、負荷に応じて動的に子プロセスを生成または終了させます。 5. **クリーンなシャットダウン/再起動**: シグナル（TERM, HUP, USR1 など）を受信すると、MPM はアクティブな接続の処理完了を待ってから、子プロセスを安全に終了させます。

*注意: シグナルハンドリングの厳密な伝播経路や、スコアボード（Scoreboard）を介した親・子プロセス間の詳細な同期フローなど、具体的なコードレベルのインタラクションは、提供されたコンテキストからは完全には特定されていません。*

重要な不変条件

  • **設定値の遵守**: 各 MPM は、設定された最小/最大アイドルスレッド数（MinSpareThreads/MaxSpareThreads）またはプロセス数（MinSpareServers/MaxSpareServers）の範囲内にアクティブなリソースを維持するように動作しなければなりません。
  • **プロセスの隔離**: prefork においては、1つのリクエスト処理のクラッシュが他の接続に影響を与えないよう、プロセス境界による完全な隔離が保証されます。

*注意: スレッドセーフティ、ロックの獲得順序、または親プロセスと子プロセス間の共有メモリ（スコアボード）の更新に関する厳密な不変条件は、提供されたコンテキストからは完全には特定されていません。*

よくある落とし穴

  • **スレッドセーフでないモジュールとマルチスレッド MPM の混用**: worker や event などのマルチスレッド環境で、スレッドセーフでないライブラリやモジュールを使用すると、メモリ汚染や予期せぬクラッシュを引き起こす原因になります。
  • **リソースの枯渇**: 最大プロセス数（MaxRequestWorkers など）の設定が不適切であると、システムメモリの枯渇（スラッシング）を招くか、あるいは逆にサーバーの処理能力を十分に引き出せなくなります。

次に読む場所

  • **include/ap_mpm.h**: MPM が提供する共通 API やクエリ機能の定義を確認する。
  • **server/mpm/prefork/prefork.c**: 最もシンプルなシングルスレッド・マルチプロセスモデルの実装を理解する。
  • **server/mpm/worker/worker.c**: スレッドとプロセスのハイブリッド管理モデルの実装を理解する。
  • **server/mpm/event/event.c**: キープアライブ接続を効率的に処理するための、高度な非同期イベント駆動モデルの実装を理解する。
