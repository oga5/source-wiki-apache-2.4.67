Connection and Request Filtering (Filter Chain)

概念

Apache HTTP Server における **Filter Chain（フィルタチェーン）** は、リクエストデータ（入力）やレスポンスデータ（出力）を段階的に処理・修飾するためのモジュール化された仕組みです。データはバケットブリゲード（apr_bucket_brigade）と呼ばれるバケットのリスト構造としてフィルタ間を受け渡されます。

フィルタは、その役割や実行される優先順位（ap_filter_type）に応じてチェーン状に連結され、入力データのデコードや出力データのヘッダ付与などの処理を順次適用します。

なぜ重要か

フィルタチェーンの仕組みにより、コアのHTTPプロトコル処理と、データの加工・検証ロジックを綺麗に分離できます。 例えば、入力フィルタである ap_http_filter は、チャンク転送エンコーディングのデコードや Content-Length に基づく境界管理、LimitRequestBody によるサイズ制限の強制を透過的に行います。これにより、後続のコンテンツハンドラは、背後の転送フォーマットやセキュリティ制限を意識することなく、安全かつ一貫した方法でリクエストボディを読み取ることができます。また、ap_http_header_filter はレスポンスヘッダの適切な構築と送信を担います。

関与するモジュール

  • module:include
  • module:modules/http
  • module:server

主要エンティティ

  • **symbol:include/util_filter.h#ap_filter_rec_t**: フィルタの定義情報（名前、実行関数、型、プロトコル制約など）を保持する構造体。next ポインタにより、登録済みフィルタのリスト構造を形成します。
  • **symbol:modules/http/http_filters.c#ap_http_filter**: HTTPリクエストボディの入力フィルタリングを行う関数。チャンクデコードや入力制限の強制を担当します。
  • **symbol:modules/http/http_filters.c#ap_http_header_filter**: HTTPレスポンスヘッダの出力フィルタリングを行う関数。

エンドツーエンドの流れ

提供されたソースコードの抜粋情報からは、接続の確立からリクエスト受信、レスポンス送信に至るフィルタチェーン全体の完全な構築・実行フロー（特に server/core_filters.c 内の具体的な処理フロー）は**完全には明らかになっていません**。

現時点で判明している部分的な流れは以下の通りです：

1. **フィルタの登録**: ap_register_input_filter や ap_register_output_filter_protocol などの登録関数を介して、ap_filter_rec_t 構造体を用いてフィルタがシステムに登録されます。 2. **入力データの処理 (ap_http_filter)**:

  • フィルタチェーンを通じて呼び出され、初回呼び出し時にコンテキスト（http_ctx_t）を初期化します。
  • Transfer-Encoding や Content-Length ヘッダに基づいて、状態（BODY_CHUNK, BODY_LENGTH など）を決定します。
  • 必要に応じて 100 Continue レスポンスを送信し、下位フィルタから ap_get_brigade を用いてデータを取得します。
  • 制限チェックやデコードを行ったデータをバケットブリゲード b に格納して上位に返します。

    • 3. **出力データの処理 (ap_http_header_filter)**:

  • レスポンス送信時に呼び出され、ap_pass_brigade や ap_set_content_length などの関数と連携して、HTTPヘッダフィールドの構築と送信を行います。

重要な不変条件

  • **フィルタのソート順**: フィルタは ap_filter_type に基づいてソートされ、適切な順序でチェーンに挿入されなければなりません。
  • **サブリクエストの制限**: AP_FTYPE_CONNECTION 以上の型を持つフィルタは、サブリクエスト内では使用できません。
  • **入力フィルタの開始状態**: ap_http_filter において、BODY_NONE 状態はトレーラヘッダ処理を除き、開始状態としては無効です。
  • **残りバイト数の管理**: Content-Length が指定されている場合、ap_http_filter のコンテキスト内の ctx->remaining は、残りの読み込み可能バイト数を正確に保持しなければなりません。

よくある落とし穴

  • **フィルタ順序の不正**: フィルタの登録順序や型定義（ap_filter_type）が不適切な場合、フィルタチェーンの実行順序が意図しないものになり、データ破損や不正なプロトコル挙動を引き起こす可能性があります。
  • **複雑な状態遷移**: ap_http_filter における ctx->state の遷移は RFC 7230 に準拠しており非常に複雑です。これを修正する際は、状態定義の整合性を慎重に確認する必要があります。
  • **メモリ管理の不備**: フィルタ処理中のメモリ管理は f->r->pool に依存しているため、バケットやブリゲードの操作時にメモリリークを引き起こさないよう注意が必要です。
  • **制限値計算の曖昧さ**: チャンク入力時における ctx->limit の計算において、チャンクオーバーヘッドと実際のデータ長の扱いに注意しないと、制限のバイパスや誤検出を招く恐れがあります。

次に読む場所

  • **include/util_filter.h**: フィルタ構造体 ap_filter_rec_t や関連するフィルタ管理APIの定義。
  • **modules/http/http_filters.c**: ap_http_filter や ap_http_header_filter の具体的な実装とHTTPプロトコルフィルタの挙動。
  • **server/core_filters.c**: コアフィルタの動作と、フィルタチェーン全体の管理機構。
