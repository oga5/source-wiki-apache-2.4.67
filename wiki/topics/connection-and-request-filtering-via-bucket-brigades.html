Connection and Request Filtering via Bucket Brigades

概念

Apache HTTP ServerにおけるI/O処理は、フィルタチェーンと「バケットブリゲード（Bucket Brigades）」と呼ばれるデータ構造を介して行われます。フィルタは、接続（Connection）やリクエスト（Request）の処理過程において、入力データ（リクエストボディなど）の読み込みや出力データ（レスポンスヘッダやボディなど）の書き込みに対して、段階的な加工や制御を適用する仕組みです。

具体的には、ap_filter_rec_t によって定義されたフィルタがチェーンを形成し、ap_http_filter のような入力フィルタがバケットブリゲード（apr_bucket_brigade）を介してデータを下位フィルタから取得・加工して上位へ渡します。

なぜ重要か

このフィルタリング機構により、コアのHTTP処理ロジックと、個別のデータ加工処理（チャンクデコード、Content-Lengthの制限、ヘッダの付与など）を疎結合に分離できます。

たとえば、ap_http_filter はリクエストボディの制限（LimitRequestBody）やチャンク転送エンコーディングのデコードをカプセル化し、ハンドラが安全かつ一貫した方法でデータを読み取れるようにします。これにより、巨大なリクエストの拒否といったセキュリティ対策や、プロトコル仕様への準拠が容易になります。

関与するモジュール

提供されたソースリファレンスに基づき、以下のモジュールが関与しています。

  • module:include (include/util_filter.h): フィルタの基本構造体やAPI定義を提供します。
  • module:modules/http (modules/http/http_filters.c): HTTPプロトコル固有の入力・出力フィルタ（ap_http_filter や ap_http_header_filter）を実装します。
  • module:server (server/core_filters.c): コアフィルタ処理を担います。

主要エンティティ

  • **symbol:include/util_filter.h#ap_filter_rec_t**: フィルタの定義情報（名前、実行関数、フィルタタイプなど）を保持する構造体。フィルタチェーンの構築や順序付けの基盤となります。
  • **symbol:modules/http/http_filters.c#ap_http_filter**: HTTPリクエストボディの入力フィルタリングを行う関数。チャンクデコードや Content-Length の境界管理、サイズ制限を行います。
  • **symbol:modules/http/http_filters.c#ap_http_header_filter**: HTTPレスポンスヘッダの出力フィルタリングを行う関数。

エンドツーエンドの流れ

提供された情報からは、接続の確立からリクエスト完了に至る完全なエンドツーエンドの制御フローの全容は完全には明らかになっていません。現時点で判明している部分的な流れは以下の通りです。

1. **フィルタの登録とチェーン構築**: ap_filter_rec_t に基づき、フィルタが登録され、フィルタタイプ（ap_filter_type）に応じてソートされたフィルタチェーンが構築されます。 2. **入力データの要求**: 上位のハンドラやフィルタが ap_get_brigade を呼び出すと、ap_http_filter などの入力フィルタが呼び出されます。 3. **データのフィルタリングとバケットブリゲードの操作**:

  • ap_http_filter は、下位フィルタから ap_get_brigade を介してデータを取得します。
  • 取得したデータに対して、Transfer-Encoding（チャンク解析）や Content-Length に基づく境界チェック、LimitRequestBody によるサイズ制限を適用します。
  • 処理されたデータは、引数で渡されたバケットブリゲード（apr_bucket_brigade）に格納されて上位へ返されます。

    • 4. **出力データの処理**: レスポンス送信時には、ap_http_header_filter などの出力フィルタが ap_pass_brigade などを呼び出して、ヘッダやボディデータを下位フィルタへ順次渡していきます。

重要な不変条件

  • **フィルタの順序**: フィルタは ap_filter_type に基づいてソートされ、適切な順序で実行される必要があります。
  • **サブリクエストの制限**: AP_FTYPE_CONNECTION 以上の型を持つフィルタは、サブリクエスト内では使用できません。
  • **リクエストボディの制限**: ap_http_filter において、Content-Length または読み込み中のデータ量が LimitRequestBody（ctx->limit）を超えた場合、HTTP_REQUEST_ENTITY_TOO_LARGE エラーを返さなければなりません（ただし、プロキシリクエストは除外されます）。
  • **状態管理の整合性**: ap_http_filter 内のコンテキスト（http_ctx_t）における ctx->remaining や ctx->state（RFC 7230準拠のチャンク状態など）は、読み込みの進行状況と厳密に同期している必要があります。

よくある落とし穴

  • **フィルタの登録順序や型の誤り**: ap_filter_rec_t で定義するフィルタの型や登録順序が不適切な場合、フィルタチェーンが意図しない順序で実行され、データの破損や不正なプロトコル挙動を引き起こす可能性があります。
  • **メモリリーク**: バケットブリゲードの操作やコンテキストの管理は f->r->pool などのメモリプールに依存しているため、バケットの生成・破棄のライフサイクルを誤るとメモリリークが発生しやすくなります。
  • **不完全な接続切断のハンドリング**: 読み込み中に接続が切断された場合（APR_INCOMPLETE）や、ノンブロッキングモードでデータが未到着の場合（APR_EAGAIN）の戻り値処理を適切に行わないと、無限ループやハングアップの原因になります。

次に読む場所

  • include/util_filter.h: フィルタの登録APIや ap_filter_rec_t の詳細な構造を確認できます。
  • modules/http/http_filters.c: ap_http_filter や ap_http_header_filter の具体的な実装、およびHTTPプロトコル制約の処理ロジックを確認できます。
  • server/core_filters.c: コアフィルタの動作や、ネットワークI/Oとバケットブリゲードの結びつきを理解するためのコードが含まれています。
