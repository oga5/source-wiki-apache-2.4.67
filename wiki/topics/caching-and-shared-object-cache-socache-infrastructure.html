Caching and Shared Object Cache (socache) Infrastructure

概念

Apache HTTP Serverにおけるキャッシュインフラストラクチャは、主に2つのレイヤーで構成されています。

1. **HTTPレスポンスキャッシュ (mod_cache)**: HTTPリクエストに対するレスポンスを効率的にキャッシュし、再利用するための高レベルな仕組みです。 2. **共有オブジェクトキャッシュ (socache)**: セッション情報や認証情報などの小規模なオブジェクトを、共有メモリ（SHMCB）やDBMなどのバックエンドにキー・バリュー形式で保存するための低レベルな抽象化レイヤーです。

ap_socache_instance_t のような不透明な（opaque）構造体を用いることで、具体的なキャッシュ実装の詳細を隠蔽し、統一されたインターフェースを介した操作を可能にしています。

なぜ重要か

キャッシュインフラストラクチャは、サーバーの応答性能向上とリソース消費の削減において極めて重要な役割を果たします。

  • **高速なレスポンス提供**: cache_quick_handler を使用することで、リクエスト処理の極めて早い段階（クイックハンドラフェーズ）でキャッシュのヒット判定を行い、重いバックエンド処理をバイパスしてレスポンスを即座に返却できます。
  • **モジュール性と拡張性**: socache インフラストラクチャにより、認証モジュール（mod_authn_socache）やその他のモジュールは、具体的なストレージの仕組み（共有メモリ、ファイルなど）を意識することなく、統一されたAPIでデータを永続化・共有できます。

関与するモジュール

主要エンティティ

  • **symbol:include/ap_socache.h#ap_socache_instance_t**: 各socacheプロバイダー実装において、個別のキャッシュインスタンスの状態を保持するための不透明な構造体。
  • **symbol:modules/cache/mod_cache.c#cache_quick_handler**: クイックハンドラフェーズにおいて、キャッシュのヒット判定、レスポンスの提供、またはキャッシュ保存用フィルタの挿入を行うメインエントリポイント。
  • **symbol:modules/cache/mod_cache.c#create_dir_config**: ディレクトリごとのキャッシュ設定構造体を生成する関数。
  • **symbol:modules/cache/mod_socache_shmcb.c#socache_shmcb_store**: 共有メモリベースの循環バッファ（SHMCB）キャッシュにデータを保存する具体的なプロバイダー関数。

エンドツーエンドの流れ

現時点では、mod_cache（HTTPレスポンスキャッシュ）と socache（小規模オブジェクトキャッシュ）の間の直接的な統合や、システム全体における完全なエンドツーエンドの連携フローは完全には明らかになっていません。

ただし、それぞれのレイヤーにおける個別の処理フローは以下の通り定義されています。

HTTPキャッシュリクエスト処理の流れ (mod_cache)

1. **リクエスト受信**: クイックハンドラフックにより cache_quick_handler が起動します。 2. **判定と検索**:

  • リクエストメソッドが GET の場合、キャッシュ検索（cache_select）を行います。
  • PUT/POST/DELETE などの場合は、キャッシュ無効化フィルタを挿入して処理を後続に委譲（DECLINED）します。

    • 3. **キャッシュヒット時**: CACHE_OUT フィルタを挿入し、既存のフィルタスタックを整理した上で、キャッシュからレスポンスを直接クライアントに送信します。 4. **キャッシュミス時**: cache_try_lock による排他制御を試み、成功すれば CACHE_SAVE および CACHE_REMOVE_URL フィルタを挿入してバックエンドからのレスポンスをキャッシュに保存する準備をします。

SHMCBキャッシュへの保存の流れ (mod_socache_shmcb)

1. **呼び出し**: ap_socache_provider_t インターフェース経由で socache_shmcb_store が呼び出されます。 2. **サブキャッシュ特定**: キー（id）のハッシュ値に基づき、対象となるサブキャッシュ領域を特定します。 3. **既存エントリ削除**: 重複を避けるため、同一IDの既存エントリを削除（shmcb_subcache_remove）します。 4. **書き込み**: 新しいデータをサブキャッシュに書き込み（shmcb_subcache_store）、統計カウンタ（新規保存数または置換数）をインクリメントします。

重要な不変条件

  • **socacheインスタンスのライフサイクル**: ap_socache_instance_t は、対応するプロバイダーの create メソッドによって生成され、かつ init メソッドが呼び出されるまでは、キャッシュ操作に使用してはなりません。
  • **認証情報のキャッシュ除外**: cache_quick_handler において、リクエストに Authorization ヘッダーが含まれている場合、そのリクエストはキャッシュ対象外として扱われます。
  • **メモリプールの局所性**: cache_quick_handler におけるすべてのメモリ割り当ては、リクエストのライフサイクルに追従するよう r->pool に紐付いている必要があります。
  • **SHMCBのキー長制限**: socache_shmcb_store に渡されるキーの長さ（idlen）は、必ず **4バイト以上** でなければなりません。

よくある落とし穴

  • **スレッドセーフティの欠如**: mod_socache_shmcb は AP_SOCACHE_FLAG_NOTMPSAFE として定義されており、socache_shmcb_store 自体は排他制御（ロック管理）を行いません。呼び出し側で適切なロック管理を行わない場合、データ破損や競合が発生する恐れがあります。
  • **キー長不足による保存失敗**: socache_shmcb_store を呼び出す際、4バイト未満のキーを渡すと APR_EINVAL エラーとなり、保存処理が即座に中止されます。
  • **ロック競合時のバイパス**: cache_quick_handler 内で cache_try_lock が失敗した場合、キャッシュの保存処理は静かにスキップされ、リクエストはバックエンドへ透過されます。この挙動をエラーと誤認しないよう注意が必要です。
