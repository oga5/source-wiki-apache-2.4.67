Shared Object Caching (socache)

概念

Shared Object Caching (socache) は、Apache HTTP Server において、セッションデータや認証資格情報などの小規模なオブジェクトをプロセス間で共有・キャッシュするための共通インターフェースおよびその実装群です。具体的なキャッシュの格納先（Memcached や共有メモリなど）を抽象化し、呼び出し側のモジュールが具体的なバックエンドの実装を意識することなく、統一された API を通じてキャッシュ操作を行えるようにします。

なぜ重要か

マルチプロセスやマルチスレッドで動作する Web サーバー環境において、プロセス間でセッション情報や認証状態を効率的に共有することは、パフォーマンスとスケーラビリティの向上に直結します。socache を利用することで、各モジュールは個別に複雑な共有メモリ管理や外部キャッシュサーバーとの通信処理を実装することなく、一貫したキャッシュ機能を容易に組み込むことができます。

関与するモジュール

  • module:include
  • module:modules/cache

主要エンティティ

  • symbol:include/ap_socache.h#ap_socache_instance_t: 各キャッシュプロバイダー（バックエンド実装）において、個別のキャッシュインスタンスの状態を保持するための不透明な（opaque）構造体。
  • symbol:modules/cache/mod_socache_memcache.c#socache_mc_store: Memcached バックエンドを使用して、指定されたキャッシュキー、データ、および有効期限をキャッシュストレージに保存する関数。
  • symbol:modules/cache/mod_socache_shmcb.c#socache_shmcb_store: 共有メモリベースの循環バッファ（SHMCB）キャッシュにデータを保存する関数。

エンドツーエンドの流れ

キャッシュを利用するモジュールは、ap_socache_provider_t インターフェースを介して ap_socache_instance_t を操作します。データの保存処理は、選択されたプロバイダーに応じて以下のように実行されます。

Memcached プロバイダーの場合 (socache_mc_store)

1. socache_mc_id2key を呼び出し、内部ID（id）を Memcached 用の文字列キーに変換します。 2. 有効期限（expiry）から現在時刻を減算し、Memcached が要求する「有効期限までの秒数」を算出します。 3. apr_memcache_set を呼び出して、データを Memcached に送信・保存します。

共有メモリ（SHMCB）プロバイダーの場合 (socache_shmcb_store)

1. キャッシュキー（id）に基づいて、対象となるサブキャッシュを特定します。 2. shmcb_subcache_remove を呼び出し、既存の同一 ID エントリを削除して置換の準備をします。 3. shmcb_subcache_store を呼び出し、新しいデータをサブキャッシュに書き込みます。 4. 書き込み成功時、置換または新規作成に応じて統計カウンタをインクリメントします。

※なお、キャッシュインスタンスの生成から破棄、およびデータの取得（retrieve）や削除（remove）を含む完全なエンドツーエンドのライフサイクル全体の流れは、提供された情報からは一部未詳です。

重要な不変条件

  • **初期化の要件**: ap_socache_instance_t は、キャッシュプロバイダーの create メソッドによって生成され、さらに init メソッドが呼び出されるまで、実際のキャッシュ操作に使用することはできません。
  • **キーの制限**:
  • Memcached 実装 (socache_mc_store) では、キー（id）は MC_KEY_LEN（254バイト）以内の文字列キーに変換可能である必要があります。
  • SHMCB 実装 (socache_shmcb_store) では、キーの長さ（idlen）は 4 以上である必要があります。
  • **有効期限の妥当性**: socache_mc_store において、有効期限（expiry）は現在時刻よりも未来（算出される秒数が 0 より大きい）でなければなりません。

よくある落とし穴

  • **スレッドセーフティの欠如**: SHMCB 実装（mod_socache_shmcb.c）は AP_SOCACHE_FLAG_NOTMPSAFE であり、socache_shmcb_store 自体は排他制御を行いません。呼び出し側で適切なロック管理を行わない場合、データ競合が発生する可能性があります。
  • **キー長制限による保存失敗**:
  • Memcached ではキーが長すぎる場合、SHMCB ではキーが 4 バイト未満の場合に、それぞれ APR_EINVAL エラーが発生して保存に失敗します。
  • **サイズ計算のオーバーフロー**: socache_shmcb_store では unsigned int を使用したサイズ計算が行われているため、極めて大きなキャッシュサイズを設定した場合にはオーバーフローのリスクがあります。
