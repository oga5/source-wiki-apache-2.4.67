Authentication and Authorization (AAA) Provider Framework

概念

Apache HTTP ServerにおけるAAA（Authentication, Authorization, Accounting）プロバイダーフレームワークは、認証（Authentication: ユーザーの身元確認）と認可（Authorization: アクセス権限の検証）の処理を分離し、コアサーバーと個別の認証・認可モジュールとの間を疎結合に連携させるためのアーキテクチャです。

このフレームワークにより、Basic認証やDigest認証などの認証方式（スキーム）と、ファイルやデータベースなどのバックエンド（プロバイダー）を柔軟に組み合わせて利用することが可能になります。

なぜ重要か

AAAフレームワークが重要な理由は、認証・認可ロジックのモジュール化と再利用性を高める点にあります。

例えば、HTTP Basic認証の仲介を行う mod_auth_basic は、具体的なパスワード検証ロジックを自身で持たず、共通インターフェースである authn_provider を介して外部のプロバイダー（ファイル、LDAP、データベースなど）に処理を委譲します。これにより、新しい認証バックエンドを追加する際も、Basic認証やDigest認証のプロトコル処理部分を再実装することなく、プロバイダーの実装のみを追加するだけで対応可能になります。

関与するモジュール

提供されたソースコード情報に基づくと、以下のモジュールが関与しています。

  • module:include: 共通の認証インターフェース定義（mod_auth.h）を提供します。
  • module:modules/aaa: 認証・認可のコア機能および具体的な認証方式の実装（mod_auth_basic.c, mod_authn_core.c, mod_authz_core.c）を提供します。

主要エンティティ

本フレームワークを構成する主要なエンティティは以下の通りです。

  • **symbol:include/mod_auth.h#authn_provider**: 認証プロバイダーが実装すべきインターフェースを定義する構造体です。パスワード検証用の check_password や、レルムベースのハッシュ取得用の get_realm_hash という関数ポインタを持ちます。
  • **symbol:modules/aaa/mod_auth_basic.c#authenticate_basic_user**: HTTP Basic認証スキームの仲介を行う関数です。リクエストから資格情報を抽出し、設定された authn_provider を順次呼び出して検証を行います。
  • **symbol:modules/aaa/mod_authn_core.c#create_authn_core_dir_config**: ディレクトリ単位の認証設定（AuthType や AuthName など）を保持する authn_core_dir_conf 構造体を生成・初期化する関数です。
  • **symbol:modules/aaa/mod_authz_core.c#authorize_user**: ユーザーの認可（Authorization）処理を担当する関数です。

エンドツーエンドの流れ

提供された情報に基づく、Basic認証におけるエンドツーエンドの処理の流れは以下の通りです。

1. **設定フェーズ**:

  • Apacheの起動・設定読み込み時に、symbol:modules/aaa/mod_authn_core.c#create_authn_core_dir_config が呼び出され、ディレクトリごとの認証設定（authn_core_dir_conf）が初期化されます。

    • 2. **リクエスト受信と認証フックの起動**:

  • クライアントからのHTTPリクエスト受信時、認証フック（ap_hook_check_authn）を介して symbol:modules/aaa/mod_auth_basic.c#authenticate_basic_user が呼び出されます。

    • 3. **資格情報の抽出と検証**:

  • authenticate_basic_user は、リクエストの AuthType が Basic であることを確認し、Authorization ヘッダーからユーザー名とパスワードを抽出します。
  • 設定された認証プロバイダー（authn_provider_list）を走査し、各プロバイダー（symbol:include/mod_auth.h#authn_provider）の check_password または get_realm_hash を呼び出して資格情報を検証します。

    • 4. **認可フェーズ**:

  • 認証が成功（OK）した後、認可処理として symbol:modules/aaa/mod_authz_core.c#authorize_user が呼び出され、アクセス権限の検証が行われます。ただし、この認可処理の具体的な内部フローや詳細なアルゴリズムは、提供された情報からは未解明です。

重要な不変条件

  • **認証タイプと設定の整合性**: symbol:modules/aaa/mod_auth_basic.c#authenticate_basic_user が動作するためには、AuthType が Basic に設定されており、かつ AuthName が設定されている必要があります。AuthName が未設定の場合は HTTP_INTERNAL_SERVER_ERROR となります。
  • **プロバイダーの戻り値**: authn_provider の各関数ポインタは、認証の成否に応じて必ず適切な authn_status（AUTH_GRANTED, AUTH_DENIED など）を返す必要があります。
  • **設定構造体のゼロクリア**: symbol:modules/aaa/mod_authn_core.c#create_authn_core_dir_config は apr_pcalloc を使用してメモリを確保するため、生成される authn_core_dir_conf 構造体は常にゼロクリアされた状態で初期化されます。
  • **認可（Authorization）の不変条件**: symbol:modules/aaa/mod_authz_core.c#authorize_user に関する詳細な不変条件や内部状態の遷移は、提供された情報からは未解明です。

よくある落とし穴

  • **AuthName の設定漏れ**: Basic認証を有効にしているにもかかわらず AuthName（レルム名）の設定を怠ると、authenticate_basic_user は HTTP_INTERNAL_SERVER_ERROR を返してリクエストを拒否します。
  • **authoritative 設定によるチェーンの遮断**: authoritative 設定が有効な場合、あるプロバイダーで認証が失敗すると、後続のプロバイダーへ処理を委譲せずに即座に HTTP_UNAUTHORIZED を返します。複数プロバイダーをフォールバックさせたい場合は、この設定の挙動に注意する必要があります。
  • **関数ポインタの NULL チェック**: authn_provider を独自に実装する際、check_password や get_realm_hash などの関数ポインタが NULL の場合、呼び出し側でのハンドリングが必要となるため、プロバイダー登録時の実装漏れに注意が必要です。

次に読む場所

  • **include/mod_auth.h**: authn_provider 構造体や authn_status などの共通AAAインターフェース定義を確認する場合。
  • **modules/aaa/mod_auth_basic.c**: HTTP Basic認証の具体的な仲介処理（authenticate_basic_user）の実装を追う場合。
  • **modules/aaa/mod_authn_core.c**: 認証設定の管理やプロバイダーの登録・管理機構（create_authn_core_dir_config）を理解する場合。
  • **modules/aaa/mod_authz_core.c**: 認可処理（authorize_user）のコアロジックを調査する場合。
